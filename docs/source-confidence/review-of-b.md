# 对方案 B 的评审（证伪向）

复算方式：逐位实现 `proposal-b.md §1` 的 `score()`（含 `§4.1` 排序键、`§4.2` 死源门限）与 `source_stat.rs:32-70` 的旧公式，对边界输入对拍。结论：**方向可采纳，公式不可落地**。

## 1. 算错的

| 输入 | 新 lcb | 新 mean | 新 ucb | n_eff | 旧公式 | 排序键（§4.1） |
|---|---|---|---|---|---|---|
| attempts=0，三通道全 0（1333 行双无证据） | 0.211 | 0.500 | 0.789 | 0 | 0.500 | **0.789** |
| 全超时 10/10，平均 30s | 0.154 | 0.365 | 0.576 | **0** | 0.150 | **0.576** |
| 只有 toc 证据 3/8（xiaxs.la） | 0.235 | 0.389 | 0.543 | 8 | 0.500 | 0.235 |
| 只有 toc 证据 2/8（janpn.net） | 0.136 | 0.278 | 0.419 | 8 | 0.500 | 0.136 |
| 只有 content 证据 5/5 | 0.812 | 0.917 | 1.000 | 5 | 0.500 | 0.812 |
| 样本=1，1/1 成功 | 0.484 | 0.726 | 0.968 | 1 | 0.914 | **0.968** |
| 100/100 成功（对照） | 0.957 | 0.963 | 0.970 | 100 | 0.881 | 0.957 |
| 145/150 但刚连败 3 次 | 0.902 | 0.916 | 0.931 | 150 | **0.05** | 0.902 |

1.1 **attempts=0**：`w=0` 走先验分支 → lcb 0.211 / ucb 0.789。而 `§4.1` 是 `n_eff<3 → ucb`，于是全部无证据源以 **0.789** 进排序键，高于现役 lcb 的 p90（B 自己算的 0.709）。`§1` 注释「无证据的源排不进队首」被 `§4.1` 当场否掉。
1.2 **缺行 fallback 并未"改走 ucb"**：`router.rs:2944/9432` 是 `unwrap_or((0.5, 3000))` 字面常量，根本不调 `score()`。实际效果是「有行无证据(0.789) > 无行(0.5)」，新源/新库被有账源压到后面 —— 与"冷启动不惩罚"相反。
1.3 **全超时**：`attempts-timeouts=0` 把搜索通道整条剔除 → `n_eff=0` → 又落进 ucb 分支 → 排序键 0.576。一个从未成功、每次 30s 超时的源排到中位之上；且 `n_eff=0 < 5`，永远进不了死源门限。
1.4 **只有 toc 证据**：方向对（0.5 → 0.235），但单通道 live 时 `w` 重归一到 1.0，`W_SEARCH=0.5/W_TOC=0.3` 只在多通道同时 live 时才生效。1698 行里 1333 行无证据、365 行有证据的绝大多数只有一条通道 → 三个权重常数对 ~95% 的行是摆设。
1.5 **只有 content 证据**：读一次书抓 5 章就算 5 个样本，与"搜索 5 次"同权；content 记账频率远高于搜索，"被读过一次的书"会被抬成 0.812。
1.6 **样本=1**：1/1 的排序键 0.968 > 100/100 的 lcb 0.957。**一次侥幸成功排到 100 次全对前面** —— 这正是 `§1` 声称要消灭的倒挂，被 `n_eff<3 → ucb` 重新造了出来。
1.7 **先验 sd 算错**：Jeffreys `Beta(0.5,0.5)` 的 var=0.125、sd=**0.354**、lcb=**0.146**；代码 `else` 分支硬编码 `1/12`（那是 `Beta(1,1)`）→ 0.211。`§1` 注释"Beta(0.5,0.5)…sd = 1/√12"把两个分布写成了一个，注释与代码必有一错。
1.8 **速度下限算错**：`0.55+0.45×(0.4+0.6e^{-x})` 的实际下界是 **0.730**，不是 `SPEED_FLOOR=0.55`（内层最小 0.4）。`§5` 说"80s 源从 0.30 抬到 ≈0.55"—— 实为 0.730。所以"慢源仍沉队尾"不成立：0.5s→0.968、84s→0.730，只差 25%（旧公式差 3.2×）；同一 48/50 源 30s 延迟下 lcb 从 0.267 变 0.672。
1.9 **consec_failures 抖动**：新公式不看它，145/150 且刚 3 连败 → 0.902（旧 0.05）。抗抖成立（见 §5），但"昨天刚坏"这个信号也一并消失。

## 2. 做不到的

2.1 **`content_bytes_*` 的写入点漏掉失败分支，且恰好漏掉要抓的那批源**。`router.rs:4806-4817` 里 `content` 确在作用域、`content.len()` 拿得到（这点成立）；但 0 字正文走 `:4850` 的失败分支（`!content.trim().is_empty()` 为 false），`content_bytes_n` 永不 +1 → `content_len_flag` 恒返回 1.0（`n<3` 不判）。FACTS §2.3 的 `17|0|OK`/`174|0|OK`/`569|0|OK` 正文都是 0 字，全部落失败分支。另 `:4780` 有正文缓存命中早退，命中也不记账。
2.2 **`last_probe_at` 的写入点是同步纯函数**：`fn dead_source_urls(&[SourceStat], i64) -> HashSet<String>`（`router.rs:9915`），两个调用点 `:2958`、`:9447` 都在搜索热路径。要写库得改 async 签名 + 传 `&storage` + 每次搜索对每个死源发一次 DB 写；`is_dead_source` 还要读 `st.last_probe_at` → `SourceStat` 加字段 → `router.rs:26522` 等 6 处测试字面量全部编译失败。
2.3 **而且这个新列是空操作**：`last_failure_at <= 6h` 已保证"6h 内动过"，死源被跳过就不再产生尝试 → 6h 后 `last_failure_at` 自然过期放行。再挂一个同为 6h 的 `last_probe_at`，放行节奏一点不变。
2.4 **修不动 FACTS §3.8**：`last_failure_at` 只有 `record_search_outcome_state` 写（`mod.rs:1790`），`record_path_outcome`（`mod.rs:1833`）只写 `updated_at`（`:1859`）。只取过目录的源 `last_failure_at=0` → `now-0 = 1.7e12 > 6h` → 即使 `n_eff>=5` 也永远进不了死源门限。`§4.2` 的「attempts → n_eff 修了口径 bug」不成立，必须同时让 `record_path_outcome` 写 `last_failure_at`（B 未提）。
2.5 **"三条流水各自衰减"做不到**：表里只有一个 `updated_at`，`record_path_outcome` 也写它（`mod.rs:1859`）。昨天取过目录、8 周前搜索过的源，陈旧搜索证据按 decay≈1 全额计入。反过来，天天被搜的源 decay 恒为 1 → 14 天半衰期对活跃源完全不生效。
2.6 **前端切 `lcb`/`n_eff` 漏了服务端**：`get_source_stats_handler`（`router.rs:4876-4887`）逐字段手写 JSON，只有 `confidence/attempts/successRate/avgLatencyMs/consecFailures/lastFailureAt`。`§4.3` 只改了 `SourcesPage.tsx`，改不动排序。
2.7 `§3` 第二阶段（章节数一致性、标题垃圾检测）依赖 `book_chapters.source_url`，B 自己承认要新增列；所以第一阶段只剩 bytes 一项，而它已被 2.1 掏空。

## 3. 自相矛盾的

3.1 **验收指标符号错了**：`§6` 表里自己的数 矛盾源 lcb 0.445、双高源最低 lcb 0.602 → **0.445−0.602 = −0.157**，文中却写 +0.157。按 `§6` 的通过线（>0），新公式**仍然倒挂**，只是从 −0.120 恶化到 −0.157。
3.2 **同一张表自打嘴巴**：「矛盾源中 lcb<=0.10（沉底）1 个」下一格写 `m.zhizihuan.com, lcb=0.142`（0.142 > 0.10）。按 `§1` 复算该源（toc=0/87、search=91/92、无 content）：age=0 → **0.522**；55 天 → 0.457；即便假设 20 次超时 + 80s 平均延迟 → 0.450。**0.142 不可达**（搜索通道 s/n≈0.99 时 mean−sd≈0.61，速度乘子下界 0.73 → lcb ≥ 0.44）。"1 个沉底"实际是 0 个。
3.3 **`§4.2` 混用了 6h 与 7 天**：条件是 `now - last_failure_at <= 6h`，统计却按"7 天内有失败 10 行"。同一段又说"现公式命中 0 个，因为 6h 窗口内没人失败"—— 新公式用同一个 6h 窗口，若 6h 内没人失败，新公式同样命中 0。
3.4 **桶计数漏了 42%**：`§6②` 说"现役 356 行里 <0.2 0 个 / 0.2-0.45 51 / >=0.45 305"，`§4.3` 却说现役 611 行。356 ≠ 611，**255 行凭空消失**。这 255 行正是 `n_eff=0` 的无证据行，lcb 一律 0.211、排序键一律 0.789 —— 所谓"中性桶塌缩"只是把 42% 的源从"都 0.5"换成"都 0.211"并挪到队首，退化桶没消失。
3.5 **"1333 行双无证据稳坐 0.4-0.6 桶（1155 行）"**：1333 > 1155，装不下。该桶里 947 行是 attempts=0（必返 0.5），只剩 208 行；另外 386 行"双无证据但 attempts>0"按 `rel` 计算，可落在任何桶（0-0.05 桶那 238 行里就可能有）。因果链不成立。
3.6 **"947 行"的真实归宿**：1698−1333=365 行有任何 toc/content 证据 → 947 行 attempts=0 里**至少 582 行三通道全空**，新公式对它们只有一个值：lcb 0.211 / mean 0.500 / ucb 0.789 / n_eff 0。即"947 行被新公式处理"的真实结果是"至少 582 行被钉成同一个 0.789 的队首大平局"。
3.7 **现役源数不一致**：FACTS 写 615，B 全篇用 611，未说明差的 4 行。
3.8 **单位从未定义**：`content.len()` 是 UTF-8 **字节**，而 FACTS §2.3 的 3215/21635/3714 全是**字**。按字比字节 → 干净章节 3215 字 = 9645 B 被当成 2.6× 中位数；按字节比字节 → `5×3714=18570 B` = 6190 字，而 `avg < 500` = 每章 167 汉字。
3.9 **"3/3 垃圾标题源（全部 < 500）"任何单位下都不成立**：569 字 > 500 字，且 569 字 = 1707 B > 500 B；174 字 = 522 B > 500 B（按字才 <500，按字节则超）。至多 1/3，而那 1 个是 0 字正文、根本不进 `content_bytes`（见 2.1）。
3.10 **`§5` 护栏自己必然红**：187 行均值 >30s。同一个 48/50 的源，30s 时旧 0.267 → 新 0.672，**Δ=0.405 > 0.25**。`§6` 断言"|new_lcb−old|>0.25 的行数 < 现役 5%"—— 光速度因子一项就让 ≥187 行（≥11% 全表；若都属现役则 30.6%）触发。

## 4. 会误伤的

4.1 **进 0.05 死源档的唯一新路径**是 `content_len_flag` 的硬 0 乘子（`lcb *= 0.0`）：一旦为 0，`lcb<=0.05 && n_eff>=5` 直接满足死源门限。具体：FACTS §2.3 的 **🌟去看小说网（5718 字/章）**。按字节口径 ≈17154 B，离 `5×3714=18570 B` 只差 8%；它本就被标注"偏大 1.8×"（即偶尔串章），均值再抬高 ~1.1 倍（≈6430 字/章）就越线 → flag=0 → lcb=0 → 6h 内一次搜索失败即进死源档、用户搜不到。而它现在是"成功"源，旧分 0.55~0.6。
4.2 **短章源同类误伤**：`avg < 500` 若按字节 = 每章 <167 汉字。公版诗文集/短篇散文源每章 100~160 字是常态 → flag=0 → 同样进死源档。
4.3 **自建源**：B 自己给的 `http://172.17.0.1:9911`（旧分 0.7）算出新 `lcb=0.199` → `<0.40 && n_eff>=3` 被前端判"差源"，相对旧分摆动 −0.50，是它自己护栏的 2 倍。B 写成"确实降了"却没处理它进差源桶。
4.4 **反向误伤更普遍：越陈旧越靠前**。衰减 + `n_eff<3 → ucb` 的组合下，同一个 5/20（成功率 25%）坏源：新鲜排序键 0.144，放 60 天变 **0.559**（+288%），高于 toc 3/8 的 xiaxs.la(0.235)；一个 20/20 的源放 60 天后排序键 **0.941**，高于 200/200 全新源的 lcb 0.935。`§6` 要消灭的倒挂，新公式在时间轴上又造了一个。

## 5. 保留的真知（应采纳）

- **删 `rich`**：`intro_count=0` 时固定 0.5，是常数项不携带信息（FACTS §3.4）；0.15 权重改给 content 有据。
- **`toc_rel/cont_rel` 缺证据不再 `else { rel }` 抄上一级**，改"无证据通道不进加权 + 权重重归一"（FACTS §3.5）—— 这是 1333 行伪中性的真实来源之一。
- **`consec_failures` 退出打分**：一次抖动 3 连败就把 145/150 的好源压到 0.05（现公式）确实该废（FACTS §3.6）。

## 6. 若要救这份方案

1. `n_eff<3 → ucb` 必须删掉，改"`n_eff<3` 一律取先验下界（0.146~0.211）"，否则队首被"无证据/陈旧/全超时"三类源占满。
2. 修 3.1 的符号错误后重跑 `§6`，先做出"矛盾源中位 − 双高源最低 > 0"再谈阈值。
3. `content_bytes` 单位与 0 字正文分支（2.1）先定死，再谈 `content_len_flag`。
